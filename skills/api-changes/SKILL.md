# /api-changes

API 변경분을 **연동하는 클라이언트 입장**에서만 서술한 문서를 Artifact로 발행한다.

## 사용법

```
/api-changes              # 인자 없음 — 이번 세션에서 만든 API, 없으면 현재 브랜치 vs main
/api-changes 123          # PR 번호
/api-changes main..HEAD   # 커밋/브랜치 범위
/api-changes <경로>       # 특정 컨트롤러/라우터 파일·디렉토리
```

## 1. 변경분 수집 (읽기 전용)

| 인자 | 소스 |
|------|------|
| 없음 | 이번 세션에서 구현·수정한 API가 있으면 그 컨텍스트를 쓴다. 없으면 `git diff $(git merge-base HEAD main)...HEAD` |
| 숫자 | `gh pr diff <n>` + `gh pr view <n> --json title,body` |
| `a..b` / `a...b` | `git diff <범위>` |
| 경로 | 해당 경로의 `git diff` + 파일 현재 내용 |

커밋·푸시·수정은 하지 않는다.

diff에서 **클라이언트 계약을 건드리는 파일만** 남긴다 — 라우트 핸들러(controller/router/route), DTO·스키마·validator, 직렬화되는 응답 타입/엔티티, API 스펙(openapi/swagger), 그리고 가드·인터셉터·미들웨어 중 **응답 형태나 인증 요구를 바꾸는 것**.

diff만으로 필드 타입·필수 여부가 확정되지 않으면 해당 DTO/타입 파일을 열어 확인한다. **추측으로 채우지 않는다** — 끝내 확인 못 한 항목은 "미확인"으로 표시한다.

## 2. 클라이언트 관점 필터 (MOST IMPORTANT)

판단 기준 한 줄: **클라이언트 코드를 고쳐야 하거나, 안 고치면 동작이 달라지는가?**

**포함**
- 엔드포인트 추가·삭제, 경로·메서드 변경
- request — path/query/body/header 필드의 추가·삭제·이름 변경·타입 변경·필수↔선택, 기본값, 검증 규칙(길이·형식·enum 값)
- response — 필드 추가·삭제·타입·nullable, 구조 변경(중첩·배열↔단일), 래핑 형태
- 상태코드, 에러 코드·에러 응답 포맷
- 인증·권한 요구 변경 (토큰 종류, 스코프, 헤더)
- 페이지네이션·정렬·필터 파라미터
- 관측 가능한 동작 변화 — 정렬 순서, 기본값, 캐시 헤더, rate limit, 비동기↔동기 전환

**제외 (내부 = 블랙박스)**
- 서비스·유스케이스·리포지토리 리팩토링, 내부 함수·클래스·변수명 변경
- DB 스키마·마이그레이션·인덱스 (응답 필드로 드러나지 않는 한)
- 트랜잭션 경계, 내부 예외 클래스, DI·모듈 구조, 아키텍처 레이어
- 로깅·메트릭·테스트·CI
- 성능 최적화 (관측 가능한 변화가 없으면)

> "내부적으로 왜 이렇게 바꿨는지"는 쓰지 않는다. **클라이언트가 무엇을 해야 하는지**만 쓴다.
> 내부 파일 경로·클래스명도 쓰지 않는다 — 프론트 개발자가 열어볼 수 없는 정보다.

## 3. 분류

엔드포인트마다 하나씩 붙인다.

- **Breaking** — 클라이언트를 안 고치면 깨진다 (필드 삭제·이름 변경·타입 변경, 필수 파라미터 추가, 경로·메서드 변경, 상태코드 변경, 검증 강화)
- **신규** — 새 엔드포인트
- **추가** — 하위호환. 안 고쳐도 되고, 쓰고 싶으면 쓴다
- **Deprecated** — 아직 동작하지만 제거 예정 (대체 경로를 반드시 명시)
- **삭제**

Breaking이 하나라도 있으면 문서 최상단에 개수와 목록을 박는다.

## 4. Artifact 발행

**작성 전 `artifact-design` 스킬을 로드한다.**

구성 (순서 고정):

1. **헤더** — 대상 서비스/API명, 기준(브랜치·PR 번호), `Breaking N · 신규 N · 추가 N` 배지
2. **먼저 할 일** — Breaking 대응 액션만 체크리스트로. 없으면 "클라이언트 수정 없이 배포 가능" 한 줄
3. **엔드포인트 카드** — Breaking → 신규 → 추가 → Deprecated → 삭제 순. 각 카드:
   - `METHOD /path` + 분류 배지 + 한 줄 설명
   - 요청 변경 표: `필드 | 변경 | 타입 | 필수 | 비고`
   - 응답 변경 표: 같은 형식
   - Before/After JSON — **바뀐 부분만**. 전체 payload 복붙 금지
   - 프론트 대응: 한두 줄
4. **에러·상태코드** — 바뀐 것만
5. **미확인 항목** — diff로 확정 못 한 것 (있을 때만)

작성 규칙:
- 한국어. 필드명·경로·타입·JSON·에러코드는 원문 유지
- 예시 값은 형식이 보이게 (`"2026-09-01T10:00:00Z"`). 실제 운영 데이터·토큰·개인정보는 넣지 않는다
- 3행 이하 표는 표 대신 문장으로
- 변경 없는 엔드포인트는 싣지 않는다

발행 후 URL과 요약 3줄(Breaking N건 / 신규 N건 / 가장 주의할 점 하나)을 보고한다.
